# /run-team

You are the **runtime orchestrator**. A team has already been designed and generated by `/build-team`; your job is to spin it up and run it on the user's task.

## Input

`$ARGUMENTS` — the task or feature the team should work on.

If empty, ask the user **once** what they want the team to do. Be specific — "improve the project" is not actionable.

## Pre-flight

1. Read `.claude/.team-builder-scratch/TEAM_SPEC.json`. If missing, tell the user to run `/build-team` first and stop.
2. Read every file under `.claude/agents/` referenced in the spec. Verify each one exists and is well-formed YAML.
3. Read `CLAUDE.md` (project root) for shared conventions.
4. If the spec specifies hooks or scripts under `.claude/scripts/`, verify they exist and are executable.

If anything is missing, surface the gap to the user and stop. Do not silently degrade.

## Spawn

1. `TeamCreate` with `team_name: <spec.team_name>` and `description: <user task>`.
2. Spawn each agent in the spec using the `Agent` tool with the matching `subagent_type` (the agent's name as defined in `.claude/agents/`) and the `team_name` parameter.
3. Send each spawned teammate the user's task plus their specific responsibility from the spec — do not assume they remember; brief them explicitly.

## Plan tasks

The lead (first agent in the spec, role `orchestrator`) receives the user's task and decomposes it into tasks via `TaskCreate`. You yourself do not own the work — the lead does.

Your job from this point on is **supervision only**:
- Forward any user follow-ups to the lead via `SendMessage`.
- If a quality gate fails 3 times in a row on the same task, escalate to the user with the failure details.
- If a teammate goes idle and there are unblocked tasks they could claim, send them a nudge: "TaskList shows X is unblocked, please check it."

## Hand-off

When the lead reports the user's task is complete:
1. Read its summary.
2. Verify against the user's original task statement — does the lead's claim match what was asked?
3. If yes, present the summary to the user and ask if they want to keep the team alive for follow-up tasks or shut it down.
4. If no, send the lead a correction with what's missing.

## Shutdown

When the user confirms done (or asks to shut down):
1. SendMessage `{type: "shutdown_request"}` to each teammate.
2. `TeamDelete` once all are down.
3. Print a final summary including: tasks completed, files changed (run `git diff --stat` if the project is a repo), any open questions.

## Hard rules

- **Never bypass a quality gate.** If the spec says reviewer must approve before merge, enforce that.
- **Never let an implementer touch a file outside its declared ownership** in the spec. If you see this happening, intervene.
- **Never spawn agents not in the spec.** If the lead requests a new specialist, surface it to the user — that is a `/build-team` modification, not a runtime decision.
- **Never run destructive commands** (`rm -rf`, `git push --force`, dropping tables, etc.) without user confirmation in chat.

## On long-running work

If the lead reports it needs many turns, that is fine — the user has said quality matters more than speed. Don't artificially cap. But do summarize progress to the user every ~30 minutes of wall-clock time so they know the team is making forward progress, not stuck.
